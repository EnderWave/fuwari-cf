刚开始学 C 语言时，我们写完代码敲一行 `gcc main.c sum.c -o prog`，可执行文件就神奇地出现了。但你有没有想过这样一个问题：

  

> 在 `main.c` 里调用 `sum()` 函数时，`sum()` 的代码明明写在另一个文件 `sum.c` 里。编译器在单独编译 `main.c` 的时候，**根本不知道 `sum()` 将来会被放在内存的哪个地址**，那它是怎么生成机器码的？

  

答案就是：**编译器先在机器码里“留空（填 0）”，并贴上一张便利贴；最后由“链接器（Linker）”把所有半成品零件拼在一起，把真正的内存地址填进空里。**

  

这篇文章就用最直白的语言，带你从零看懂「链接」到底是怎么把多个 `.c` 文件组装成可执行程序的。

  

## 1. 从源码到可执行程序：四步流水线

  

假设我们有两个简单的源文件 `main.c` 和 `sum.c`：

  

```c title="main.c"

int sum(int *a, int n);

int array[2] = {1, 2};

  

int main() {

    int val = sum(array, 2);

    return val;

}

```

  

```c title="sum.c"

int sum(int *a, int n) {

    int i, s = 0;

    for (i = 0; i < n; i++) {

        s += a[i];

    }

    return s;

}

```

  

当我们运行 `gcc -Og -o prog main.c sum.c` 时，`gcc` 本身其实是个“包工头（编译驱动程序）”，它会在后台依次喊 4 个工人出来干活：

  

| 阶段 | 工具名称 | 输入 $\to$ 输出 | 通俗理解它在干什么 |

| :--- | :--- | :--- | :--- |

| **1. 预处理** | 预处理器 `cpp` | `main.c` $\to$ `main.i` | 把 `#include` 的头文件内容直接粘贴进来，把 `#define` 宏替换掉，去掉注释 |

| **2. 编译** | 编译器 `cc1` | `main.i` $\to$ `main.s` | 把 C 语言翻译成人类还能勉强看懂的**汇编语言** |

| **3. 汇编** | 汇编器 `as` | `main.s` $\to$ `main.o` | 把汇编指令直接翻译成机器码，打包成**半成品零件（可重定位目标文件 `.o`）** |

| **4. 链接** | 链接器 `ld` | `main.o` + `sum.o` $\to$ `prog` | 把多个 `.o` 半成品零件组装起来，填好所有跨文件调用的地址，生成**成品（可执行文件）** |

  

### 为什么不直接把所有代码一起编译，非要搞个“链接器”？

  

1. **模块化（好管理）**：几万行的项目可以拆成几十个小的 `.c` 文件，还能把常用功能（比如数学函数 `sin`/`cos`、打印函数 `printf`）打包成公共库给所有人用。

2. **省时间（增量编译）**：如果你有 100 个 `.c` 文件，只改了其中 1 个，只需要重新编译这 1 个 `.o` 文件，再花零点几秒重新链接即可，不用把另外 99 个文件重编一遍。

3. **省空间（按需取用）**：标准库里有上千个函数，链接器只会把你程序里**真正调用了的那几个函数**挑出来塞进最终程序里。

  

### 链接器只干两件核心大事

  

> [!IMPORTANT]

> 整章内容其实就是在讲链接器干的这两件事：

> 1. **符号解析（Symbol Resolution，对名单）**：`main.o` 喊了一句“我要调用 `sum`”，链接器去所有 `.o` 文件的名册里找，确认 `sum` 到底定义在哪个 `.o` 文件里。

> 2. **重定位（Relocation，填地址）**：把所有 `.o` 文件合并排列好，给每个函数和全局变量分配真正的内存门牌号，然后回头把之前机器码里留空的 `00 00 00 00` 改成真实地址。

  

## 2. 目标文件与 ELF 格式：拆开 `.o` 零件盒看看

  

### 2.1 三种目标文件（它们在 Linux 下都叫 ELF 文件）

  

- **可重定位目标文件（`.o`）**：每个 `.c` 文件单独编译出来的**半成品零件**，里面的地址都还是从 `0` 开始的临时编号，不能直接运行。

- **可执行目标文件（如 `prog` / `a.out`）**：链接器组装好的**成品**，地址已经全部填好，双击或在终端输入 `./prog` 就能直接装进内存跑起来。

- **共享目标文件（`.so`，Windows 下叫 `.dll`）**：一种特殊的半成品零件（动态库），不用在编译时焊死在程序里，等程序运行起来以后再动态加载进内存。

  

### 2.2 ELF 文件的“分类收纳盒”结构

  

Linux 用一种叫 **ELF（Executable and Linkable Format）** 的标准格式来存放上述三种文件。你可以把一个 `.o` 文件想象成一个**分格子的收纳盒**，不同性质的东西放进不同的格子里（每个格子叫一个 **Section，节**）：

  

| 节（格子）名称 | 里面装的是什么？ | 初学者最容易踩坑的细节 |

| :--- | :--- | :--- |

| **`.text`** | 已编译好的**机器指令代码** | 只读、可执行 |

| **`.rodata`** | **只读数据**（Read-Only Data） | 比如 `printf("Hello\n")` 里的字符串常量、以及 `switch-case` 生成的跳转表 |

| **`.data`** | **已经赋了初值**的全局变量和 `static` 变量 | 比如 `int array[2] = {1, 2};` |

| **`.bss`** | **没有赋初值**（或初值为 `0`）的全局变量和 `static` 变量 | 巧记：**"Better Save Space"（省空间）**！因为初值全是 0，没必要在硬盘文件里真存几万个 0，所以在磁盘文件里**不占任何实际体积**，只记个大小，等程序运行时再去内存里开空间清零 |

| **`.symtab`** | **符号表（Symbol Table，花名册）** | 记录这个文件里定义了哪些函数/全局变量，又引用了哪些外部名字。**注意：普通局部变量不在里面！** |

| **`.rel.text`** | `.text` 代码里的**填空题便利贴** | 记录机器码里哪些位置留了空（比如调用外部函数 `sum`），等链接时要怎么把地址填进去 |

| **`.rel.data`** | `.data` 数据里的**填空题便利贴** | 如果某个全局指针初始值指向了别处的变量（如 `int *p = &buf[0];`），这里记录需要修正的指针位置 |

  

## 3. 第一步：符号解析（对花名册与强弱符号）

  

### 3.1 什么是“符号（Symbol）”？为什么普通局部变量不是符号？

  

在链接器眼里，**“符号”就是函数名或变量名**。它只关心三类符号：

1. **全局符号（Global）**：本文件定义、别人也能用的（不带 `static` 的函数和全局变量，比如 `main`、`array`）。

2. **外部符号（External）**：别人定义、本文件拿来用的（比如 `main.c` 里调用的 `sum`）。

3. **局部符号（Local）**：加了 **`static` 关键字**的函数和变量，只能在本文件内部使用。

  

> [!WARNING]

> **新手最常困惑的问题：`int main() { int val = 1; }` 里的 `val` 是局部符号吗？**

> **不是！** 函数里不加 `static` 的普通局部变量（比如 `val`、`i`、`s`），在程序运行时是临时分配在**栈（Stack，就像草稿纸）**上的，函数一结束就擦掉了。**链接器根本不知道普通局部变量的存在**，它们也绝不会出现在符号表 `.symtab` 里！

>

> **那如果函数里写了 `static int x = 0;` 呢？**

> 加了 `static` 的变量需要“出了函数也不销毁，下次进来还记得上次的值”，所以它不能放草稿纸（栈）上，而是被放进了固定的 `.data` 或 `.bss` 节里。如果在同一个 `.c` 文件的两个函数 `f()` 和 `g()` 里都写了 `static int x;`，编译器为了防止它们重名打架，会偷偷在符号表里把它们改名为 `x.1` 和 `x.2`！

  

### 3.2 动手看一道真题：Practice Problem 7.1

  

看下面这段 `swap.c` 代码，判断里面的 5 个名字会不会进 `swap.o` 的符号表 `.symtab`，以及会分到哪个节：

  

```c title="swap.c"

extern int buf[];       // 1. 声明外部数组 buf（定义在另一个文件 m.c 里）

int *bufp0 = &buf[0];   // 2. 已初始化的全局指针

int *bufp1;             // 3. 未初始化的全局指针

  

void swap() {           // 4. 函数定义

    int temp;           // 5. 函数内的普通局部变量

    bufp1 = &buf[1];

    temp = *bufp0;

    *bufp0 = *bufp1;

    *bufp1 = temp;

}

```

  

先自己想一想，再点击黑幕对答案：

  

| 名字 | 会进 `.symtab` 符号表吗？ | 符号类型 | 定义在哪个模块？ | 分到哪个节（Section）？ |

| :--- | :--- | :--- | :--- | :--- |

| `buf` | :spoiler[会（Yes）] | :spoiler[外部符号 extern] | :spoiler[m.o] | :spoiler[在 m.o 中属于 .data（在 swap.o 符号表里标为 UND 未定义）] |

| `bufp0` | :spoiler[会（Yes）] | :spoiler[全局符号 global] | :spoiler[swap.o] | :spoiler[.data（因为已经赋了初值 &buf[0]）] |

| `bufp1` | :spoiler[会（Yes）] | :spoiler[全局符号 global] | :spoiler[swap.o] | :spoiler[COMMON（未初始化的全局变量，弱符号）] |

| `swap` | :spoiler[会（Yes）] | :spoiler[全局符号 global] | :spoiler[swap.o] | :spoiler[.text（因为是函数代码）] |

| `temp` | :spoiler[不会（No）] | :spoiler[—] | :spoiler[—] | :spoiler[—（普通局部变量在栈上，链接器完全看不见它）] |

  

### 3.3 两个文件定义了同名全局变量怎么办？——强弱符号规则

  

如果 `p1.c` 和 `p2.c` 里不小心起了相同的名字，链接器怎么决定听谁的？

Linux 把全局符号分成两类：

- **强符号（Strong，有准信的）**：所有的**函数**、以及**赋了初值的全局变量**（如 `int foo = 5;`）。

- **弱符号（Weak，没准信占座的）**：**没有赋初值的全局变量**（如 `int foo;`）。

  

> [!IMPORTANT]

> **强弱符号的三条铁律：**

> - **规则 1（一山不容二虎）**：不允许有多个同名的**强符号**。比如两个文件都定义了函数 `p1(){}` 或都写了 `int x = 1;`，链接器直接报错停止！

> - **规则 2（有强听强的）**：如果有一个**强符号**和多个同名的**弱符号**，统统听**强符号**的！

> - **规则 3（全弱随便挑）**：如果有多个同名的**弱符号**，链接器随便挑一个（注：现代 GCC 10+ 默认开启了 `-fno-common`，遇到多个同名弱符号也会直接报错保护你，但考试必考传统规则！）。

  

#### 为什么规则 2 和 3 会引发极其隐蔽的 Bug？（经典考题）

  

看下面这个恐怖的例子：

  

```c title="模块 1 (p1.c)"

int x = 7; // 强符号，int 占 4 个字节

int y = 5; // 强符号，紧挨着 x 后面存放（占 4 个字节）

```

  

```c title="模块 2 (p2.c)"

double x;  // 弱符号！程序员以为自己定义了一个 8 字节的 double

void p2() {

    x = 3.14159; // 灾难发生！

}

```

  

**发生了什么？**

1. 链接时，模块 1 的 `int x = 7` 是强符号，模块 2 的 `double x` 是弱符号。根据**规则 2**，链接器让模块 2 里的 `x` 直接指向了模块 1 里那个只有 **4 字节**的 `int x` 的地址！

2. 当 `p2()` 执行 `x = 3.14159` 时，它往 `x` 的地址强行写入了 **8 个字节**的 `double` 数据——前 4 个字节改掉了 `x`，**后 4 个字节直接把住在隔壁的无辜变量 `y` 给覆盖掉了**！

  

> [!TIP]

> **怎么彻底避开这种坑？**

> 1. 尽量别用全局变量；

> 2. 只在本文件里用的全局变量，一定加上 **`static`**（变成私有局部符号，绝不跟别的文件冲突）；

> 3. 定义全局变量时**顺手赋个初值**（比如 `int x = 0;`，直接变成强符号，万一重名立刻报错提醒你）；

> 4. 借用别的文件的全局变量时，老老实实写上 **`extern`**。

  

## 4. 第二步：重定位（怎么把留空的地址填上去？）

  

对完花名册后，链接器把所有 `.o` 文件的 `.text` 拼成一个大的 `.text`，`.data` 拼成一个大的 `.data`。这时，每个函数和全局变量终于拿到了自己最终在虚拟内存里的**真实门牌号（运行时地址）**。

  

接下来就是**把之前机器码里填 `0` 的空白处，改成真正的地址**。我们直接拿课件里最经典的 `main.o` 反汇编来手算一遍，算完你就彻底懂了！

  

### 4.1 观察重定位前的“半成品” `main.o`

  

运行 `objdump -r -d main.o`，看看汇编器留下的两个“填空题”：

  

```text title="objdump -r -d main.o（链接前的半成品）" {4,5,6,7}

0000000000000000 <main>:

   0: 48 83 ec 08          sub    $0x8,%rsp

   4: be 02 00 00 00       mov    $0x2,%esi

   9: bf 00 00 00 00       mov    $0x0,%edi          # 把 array 的地址放进 %edi（现在后4字节全是 00！）

                        a: R_X86_64_32   array       # 便利贴1：在偏移 0xa 处填入 array 的 32 位绝对地址

   e: e8 00 00 00 00       callq  13 <main+0x13>     # 调用 sum（e8 是 call 指令，后面4字节全是 00！）

                        f: R_X86_64_PC32 sum-0x4     # 便利贴2：在偏移 0xf 处填入 sum 的 PC 相对偏移（带 -4）

  13: 48 83 c4 08          add    $0x8,%rsp

  17: c3                   retq

```

  

仔细看第 4～7 行：

- 在偏移 `9:` 处，机器码是 `bf 00 00 00 00`。其中 `bf`（占 1 字节，位于偏移 `0x9`）代表 `mov ..., %edi`；紧跟着从偏移 **`0xa`** 开始的 4 个字节 `00 00 00 00` 就是留给 `array` 地址的**第一个填空框**！

- 在偏移 `e:` 处，机器码是 `e8 00 00 00 00`。其中 `e8`（占 1 字节，位于偏移 `0xe`）代表 `callq` 指令；紧跟着从偏移 **`0xf`** 开始的 4 个字节 `00 00 00 00` 就是留给 `sum` 函数地址的**第二个填空框**！

  

### 4.2 手算填空：绝对寻址 vs PC 相对寻址

  

现在，链接器排好座位了，告诉我们三个已知条件：

- `main` 函数所在的 `.text` 节被放在了起始地址 **`0x4004d0`**；

- `sum` 函数被放在了地址 **`0x4004e8`**；

- 全局数组 `array` 被放在了地址 **`0x601018`**。

  

#### 填空 1：32 位绝对地址（`R_X86_64_32`）——最简单，直接填门牌号！

  

便利贴 1 说：在偏移 `0xa` 的框里，用 `R_X86_64_32`（绝对地址）方式填入 `array` 的地址。

既然 `array` 的真实门牌号就是 `0x601018`，那直接把 `0x00601018` 填进框里就完事了！（因为 x86 是小端序，低位字节在前，所以机器码写成 `bf 18 10 60 00`）。

  

#### 填空 2：PC 相对地址（`R_X86_64_PC32`）——为什么要减 4？

  

便利贴 2 说：在偏移 `0xf` 的框里，用 `R_X86_64_PC32`（PC 相对寻址）方式填入 `sum` 的偏移量，后面还跟了个奇怪的 **`-0x4`（即 `addend = -4`）**。

  

> [!NOTE]

> **用“迈步走”一眼看懂 PC 相对寻址和 `-4`：**

> 1. **CPU 是怎么执行 `callq` 的？**

>    当 CPU 读完这整条 5 字节的 `callq` 指令（1 字节 `e8` + 4 字节填空框）时，CPU 的程序计数器（`PC`）**已经站在了下一条指令 `add $0x8, %rsp` 的门口**！然后 CPU 会把 **`PC` 当前的值 + 框里填的数**，作为跳转的目标地址。

> 2. **所以框里到底该填什么数？**

>    框里填的数 = **目标 `sum` 的地址 $-$ 下一条指令 `PC` 的地址**！

> 3. **那下一条指令 `PC` 的地址是多少？**

>    - `main` 起点是 `0x4004d0`，填空框的起点 `refaddr` 是 `0x4004d0 + 0xf = 0x4004df`。

>    - 因为填空框本身占 **4 个字节**（`0x4004df`、`e0`、`e1`、`e2`），跨过这 4 个字节的填空框，就是下一条指令 `PC` 的地址：`0x4004df + 4 = 0x4004e3`！

>    - 所以：

>      $$\text{框里填的数} = \text{sum 地址 } (\text{0x4004e8}) - \text{下一条指令地址 } (\text{0x4004e3}) = \text{0x5}$$

>    - 你看，公式写成 $\text{ADDR}(\text{sum}) + (-4) - \text{refaddr}$，里面的 **$-4$ 其实就是为了抵消填空框自身的 4 个字节宽度**（因为 $\text{refaddr} - (-4) = \text{refaddr} + 4 = \text{下一条指令地址 PC}$）！

  

填完这两个空后，用 `objdump -dx prog` 看最终的可执行文件，严丝合缝：

  

```text title="objdump -dx prog（链接后的成品）" {4,5}

00000000004004d0 <main>:

  4004d0: 48 83 ec 08          sub    $0x8,%rsp

  4004d4: be 02 00 00 00       mov    $0x2,%esi

  4004d9: bf 18 10 60 00       mov    $0x601018,%edi     # 已填入 array 的绝对地址 0x601018

  4004de: e8 05 00 00 00       callq  4004e8 <sum>       # 已填入相对偏移 0x5 (0x4004e3 + 0x5 = 0x4004e8)

  4004e3: 48 83 c4 08          add    $0x8,%rsp          # 执行 callq 时 PC 指向这里 (0x4004e3)

  4004e7: c3                   retq

```

  

### 4.3 趁热打铁：10 秒钟口算 Practice Problem 7.5

  

题目：假设 `m.o` 的 `.text` 节被放在了 `0x4004d0`，目标函数 `swap` 被放在了 `0x4004e8`。`callq swap` 的填空框偏移量是 `r.offset = 0xa`（类型 `R_X86_64_PC32`，`r.addend = -4`）。请问填空框里应该填多少？

  

- **第 1 步（找填空框地址）**：`0x4004d0 + 0xa = 0x4004da`

- **第 2 步（跨过 4 字节找下一条指令 `PC`）**：`0x4004da + 4 = 0x4004de`

- **第 3 步（目标地址减 `PC`）**：:spoiler[0x4004e8 - 0x4004de = 0xa！所以框里填 0xa（小端序机器码为 0a 00 00 00）。是不是超简单？]

  

## 5. 静态库（`.a`）与动态共享库（`.so`）

  

平时我们写的每个程序都要用 `printf`、`malloc`。怎么把这些常用函数打包提供给程序员呢？有两种方案：

  

### 5.1 静态库（`.a`）：像“把菜谱复印进每本书里”

  

静态库（`.a` 文件）其实就是用 `ar` 工具把一大堆 `.o` 文件打包成一个压缩包（比如 `libc.a` 里装了 1496 个 `.o` 文件）。当你链接时，如果你只用到了里面的 `addvec.o`，链接器就会单独把 `addvec.o` 从包里抽出来，复印一份塞进你的可执行程序里：

  

```bash title="制作并使用静态库 libvector.a"

gcc -c addvec.c multvec.c                # 1. 编译出两个 .o 零件

ar rs libvector.a addvec.o multvec.o     # 2. 打包成静态库 libvector.a

gcc -c main2.c                           # 3. 编译主程序 main2.o

gcc -static -o prog2c main2.o -L. -lvector # 4. 链接（-L. 表示在当前目录找，-lvector 对应 libvector.a）

```

  

> [!CAUTION]

> **必考大坑：为什么静态库 `-lxxx` 必须写在 `gcc` 命令行的最后面？**

> 想象链接器是一个**“不走回头路的采购员”**，手里拿着一张**“待办缺货清单”**从左往右逛命令行上的每个文件：

> - **正确写法 `gcc -L. libtest.o -lmine`**：采购员先看 `libtest.o`，发现里面调用了 `libfun` 但没定义，赶紧把 `libfun` 记在“缺货清单”上；接着往右走到 `-lmine`（`libmine.a`），照着清单把 `libfun.o` 提出来，完美收工！

> - **错误写法 `gcc -L. -lmine libtest.o`**：采购员一上来先路过 `-lmine` 库房，但此时他的**缺货清单还是空的**，于是他两手空空走出了库房；紧接着走到 `libtest.o`，发现缺了 `libfun`，但后面已经没有文件了，采购员绝不回头，直接报错 `undefined reference to 'libfun'`！

  

### 5.2 动态共享库（`.so`）：像“大家共用图书馆里的同一本书”

  

静态库虽然好用，但如果电脑上有 500 个程序都用了 `printf`，磁盘和内存里就会存 500 份一模一样的 `printf` 机器码！为了解决这个问题，现代系统默认都用**动态共享库（`.so`）**：

  

1. **加载时动态链接（最常见）**：编译生成可执行文件时，不把 `.so` 的代码复制进去，只记个名字。等运行 `./prog` 时，系统自动叫来动态链接器 `ld-linux.so`，把共享库映射到内存里供所有进程共享。

   ```bash title="制作并使用动态库 libvector.so"

   gcc -shared -fpic -o libvector.so addvec.c multvec.c

   gcc -o prog2l main2.c ./libvector.so

   ```

2. **运行时动态链接（插件机制）**：程序都已经跑起来了，在代码里临时用 `dlopen("libvector.so", RTLD_LAZY)` 打开一个 `.so` 文件，用 `dlsym(handle, "addvec")` 拿到函数指针直接调用（就像很多游戏动态加载 Mod 插件一样）。

  

## 6. 实战黑科技：库打桩（Library Interpositioning）

  

懂了链接的三个时机（编译时、链接时、加载/运行时），你就能玩转一个极其酷炫的技能——**库打桩（拦截函数调用）**。

  

**场景**：别人给你一个写好的程序 `int.c`，里面调用了系统的 `malloc` 和 `free`。现在要求你**不准修改 `int.c` 的代码**，但每次它调用 `malloc` 和 `free` 时，都要在屏幕上偷偷打印出分配了多少字节、地址是多少（用来查内存泄漏）。

  

我们可以在三个不同的阶段“设卡拦截”：

  

| 拦截阶段 | 通俗原理（怎么偷梁换柱的？） | 需要什么条件？ | 核心命令 |

| :--- | :--- | :--- | :--- |

| **1. 编译时打桩** | 写个假头文件 `malloc.h`，用 `#define malloc(x) mymalloc(x)` 把源码里的名字直接替换掉 | 需要拿到 `.c` 源码重新编译 | `gcc -I. -o intc int.c mymalloc.o` |

| **2. 链接时打桩** | 给链接器传暗号 `--wrap,malloc`，让它把所有的 `malloc` 连到 `__wrap_malloc` 上，而把 `__real_malloc` 连到真 `malloc` 上 | 需要拿到 `.o` 文件重新链接 | `gcc -Wl,--wrap,malloc -Wl,--wrap,free -o intl int.o mymalloc.o` |

| **3. 运行时打桩** | **最强大！** 用环境变量 `LD_PRELOAD="./mymalloc.so"` 让动态链接器优先加载我们的假库，在假库里用 `dlsym(RTLD_NEXT, "malloc")` 找到排在后面的真 `malloc` | **什么都不需要！** 直接对现成的可执行文件生效 | `LD_PRELOAD="./mymalloc.so" ./intr` |

  

这三种打桩的代码非常简短，对比着看一目了然：

  

```c title="三种打桩方式核心代码对比 (mymalloc.c)"

/* ========== 方式 1：编译时打桩（配合 malloc.h 里的 #define 宏替换） ========== */

#ifdef COMPILETIME

#include <stdio.h>

#include <malloc.h>

void *mymalloc(size_t size) {

    void *ptr = malloc(size);            // 调用真正的 libc malloc

    printf("malloc(%d)=%p\n", (int)size, ptr);

    return ptr;

}

#endif

  

/* ========== 方式 2：链接时打桩（配合 gcc -Wl,--wrap,malloc） ========== */

#ifdef LINKTIME

#include <stdio.h>

void *__real_malloc(size_t size);        // 声明真正的 malloc

void *__wrap_malloc(size_t size) {       // 拦截所有对 malloc 的调用

    void *ptr = __real_malloc(size);

    printf("malloc(%d) = %p\n", (int)size, ptr);

    return ptr;

}

#endif

  

/* ========== 方式 3：运行时打桩（配合 LD_PRELOAD="./mymalloc.so"） ========== */

#ifdef RUNTIME

#define _GNU_SOURCE

#include <stdio.h>

#include <stdlib.h>

#include <dlfcn.h>

void *malloc(size_t size) {

    // 去下一个共享库（即 libc.so）里找出真正的 malloc 函数地址

    void *(*mallocp)(size_t) = dlsym(RTLD_NEXT, "malloc");

    char *ptr = mallocp(size);

    printf("malloc(%d) = %p\n", (int)size, ptr);

    return ptr;

}

#endif

```
